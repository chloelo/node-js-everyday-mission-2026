## **題目**

> 團隊裡目前開發資料庫的資料表，都是每個工程師自己手動在資料庫裡執行 SQL 建出來的，沒有留下任何紀錄檔案。有一天，正式環境要開一個新的測試環境，卻沒有人能一次講清楚目前的資料表結構總共長什麼樣子、之前改過哪些欄位。

請根據以上情境，回答下列問題：

1. 這個團隊目前遇到的問題，跟今天學到的哪個概念直接相關？如果導入這個做法，能解決情境裡描述的哪些困擾？
2. 如果之後要幫某張資料表新增一個欄位，導入 migration 之後，正確的做法應該是「回去修改原本建立這張表的那份 migration」，還是「另外寫一份新的 migration 來新增欄位」？為什麼？
3. 「開發階段的資料庫可以安全重置」跟今天學到的哪個特性有關？如果沒有這個做法，重置資料庫會有什麼風險或麻煩？


## 回答

### 1.

這跟 Migration 有關。

現在大家都是自己手動建表、改欄位，沒有留下紀錄，所以之後很難知道資料表以前改過什麼，也沒辦法很確定不同環境的資料表結構是不是一樣。

導入 Migration 之後，每次建立或修改資料表都會留下一份紀錄。之後不管是新人接手，還是要建立新的測試環境，都可以照著 Migration 依序執行，建立出一樣的資料表結構。

### 2.

應該另外寫一份新的 Migration。

例如原本有：

    20260615_create_classes_table.sql

之後要新增 `teacher` 欄位，就再建立：

    20260616_add_teacher_to_classes.sql

裡面寫：

    ALTER TABLE classes ADD COLUMN teacher VARCHAR(50);

不要回去修改原本的 Migration，因為原本的 Migration 已經代表當時做過的修改。如果回頭改掉，之後就看不到資料表是怎麼一步一步變成現在的樣子。

### 3.

這跟 Migration 有完整的紀錄，可以重新建立資料表結構有關。

如果開發時把資料庫清掉，只要再按照 Migration 的順序執行一次，就可以把資料表重新建回來。

如果沒有 Migration，重置之後就只能靠自己回想以前做過哪些修改，再一個一個手動建回去，很容易漏掉欄位或其他設定，最後重建出來的結構可能跟原本不一樣。
